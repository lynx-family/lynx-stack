Lynx `debug-metadata.json` 格式的 schema 类型与解析辅助函数。

此包刻意保持小巧且零依赖，可以安全地在 Rsbuild 插件、dev server 中间件、反符号化服务、调试 CLI 以及其他任何需要读取该格式的地方引入。产出方（目前只有 `@lynx-js/debug-metadata-rsbuild-plugin`）引入的是同一套类型，因此 schema 始终是唯一的事实来源。

## 函数 \{#\}

### `assertUiNode()` \{#assertuinode\}

```ts
assertUiNode(value: unknown, path: string): asserts value is UiNode
```

断言一个解析后的值是 [`UiNode`](#uinode) 树。
请在信任边界处使用——例如刚对引擎导出的数据执行 `JSON.parse` 之后——
使格式错误的输入尽早失败并给出带位置的错误（`$.children[1]` 形式的路径），
而不是在反向解析的深层逻辑中崩溃。

`nodeIndex`、`debugMetadataUrl` 和 `children` 均为可选
（引擎会产出不带源码映射的节点，例如原始文本）；
仅当它们存在且类型错误时才会被拒绝。非对象值，或
`children` 不是数组时，总会被拒绝。

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `value` | `unknown` |  |
| `path` | `string` |  |

**返回值：** `asserts value is UiNode`

## 常量 \{#\}

### `FIELDS` \{#fields\}

```ts
const FIELDS: Map<string, FieldResolver>
```

字段名 → resolver 的映射。**HTTP 层直接读取该对象。**
修改会在下一次请求时生效——该导出是一个实时的 `Map`，
插件可以在启动时注册自己的字段。

新增字段只需一行 `FIELDS.set('your-name', { ... })`。

### `UI_SOURCE_MAP_RECORDS_BUILD_INFO` \{#ui-source-map-records-build-info\}

```ts
const UI_SOURCE_MAP_RECORDS_BUILD_INFO: "lynxUiSourceMapRecords"
```

主线程 loader 会将从模块中提取出的
[`UiSourceMapRecord`](#uisourcemaprecord) 数组暂存在 `module.buildInfo[UI_SOURCE_MAP_RECORDS_BUILD_INFO]` 中，
供 `LynxDebugMetadataPlugin` 收集。

该常量位于这个零依赖的 schema 包中，使生产方
（`@lynx-js/react-webpack-plugin` 的 loader）和使用方
（`@lynx-js/debug-metadata-rsbuild-plugin`）都能读取同一个常量，
而无需在运行时互相依赖。

## 类型 \{#\}

### `Artifact` \{#artifact\}

构建产生的产物，至少携带一个
调试数据源。

标识为 `(filename, tasmSection)`：
  - `filename` 是资源文件名（basename，例如 `main-thread.js`、
    `background.fd311de1.js`、`main.css`）。
  - `tasmSection` 是该产物在
    `tasm.json` 中的位置，用于区分文件名模式相同、
    但位于不同 section 的产物。

`tasmSection` 是由嵌套对象各级 key 组成的路径数组，因为原始
key（尤其是 `customSections` 下的 key）本身可能包含点号，
无法安全地合并为以点号分隔的字符串。示例：

  - `['lepusCode', 'root']`        main-thread.js
  - `['lepusCode', 'chunks', '0']` 异步主线程 chunk
  - `['manifest', '/<asset-name>']` 后台 JS bundle
  - `['customSections', 'data.v2']` key 中含点号的自定义 section
  - `['css']`                      CSS 产物

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| <a id="artifact-debugsources"></a>`debugSources` | [`DebugSource`](#debugsource)`[]` | 该产物的调试数据源，顺序与 反向符号化（reverse symbolication）的解码链一致。 使用方从运行时位置出发、希望还原原始源码时， 按从左到右的顺序遍历此列表： 1. `bytecode-debug-info`（如果存在）将字节码 PC 偏移    映射回编码后 JS 源码的 `(line, column)`。 2. 随后 `source-map` 将该 `(line, column)` 映射回    原始编写的文件。 |
| <a id="artifact-filename"></a>`filename` | `string` | 该产物的寻址名称：产出文件的文件名（basename）， 或当 bundle 将其作为自定义 section 携带时的 section 名称。 |
| <a id="artifact-kind"></a>`kind` | `"main-thread" \| "background" \| "css"` | 该资源在 `tasm.json` 中所属的 encoder 分类： - `main-thread` — 运行在 lepusNG 主线程上的 JS   （编译进 `lepusCode` section）。 - `background` — 运行在后台 JS 引擎上的 JS   （位于 `manifest` section）。 - `css` — 抽取出的 CSS chunk（位于 `css` section）。 |
| <a id="artifact-path"></a>`path` | `string` | 产出资源本身相对于 bundler 的路径（例如 `.lynx/main/main-thread.js`）。区别于 [`SourceMapDebugSource.path`](#sourcemapdebugsource)，后者指向 同级的 `.map` 文件。 |
| <a id="artifact-tasmsection"></a>`tasmSection?` | `string[]` |  |

编译为 lepusNG

| 成员 | 类型 | 说明 |
| --- | --- | --- |

### `DebugMetadataAsset` \{#debugmetadataasset\}

每个 Lynx template 入口产出的完整 `debug-metadata.json` 数据。

不对称说明：`artifacts[]` 是**按产物**组织的（每个 JS /
CSS / 字节码 bundle 一项），而 `uiSourceMap` 是**按入口**组织的
（每个入口的运行时 UI 树恰好对应一份 UI source map）。强行将
`uiSourceMap` 放入 `artifacts[]` 需要虚构一个合成产物，
混淆运行时概念与构建产物。

不同的使用方读取不同的字段：
  - JS 错误反向符号化遍历 `artifacts[]`，查找
    `kind: 'source-map'` 的调试数据源。
  - 主线程字节码反向符号化遍历 `artifacts[]`，
    查找 `kind: 'bytecode-debug-info'` 以及对应的 `source-map`。
  - UI 元素检查器直接读取 `uiSourceMap`。

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| <a id="debugmetadataasset-artifacts"></a>`artifacts` | [`Artifact`](#artifact)`[]` | 每个携带调试数据的构建产物对应一项。 当产出方尚未接入填充逻辑时为空； 使用方应将空数组视为“没有可用的源码级调试数据”， 而非错误。 |
| <a id="debugmetadataasset-buildinfo"></a>`buildInfo` | `{ git?: `[`GitMetadata`](#gitmetadata)`; rspeedy?: `[`RspeedyMeta`](#rspeedymeta)` }` | 构建时 / 上下文信息。目前为封闭结构—— 如需扩展，请在该接口中添加具名字段（并升级 schema）， 而不是在运行时塞入任意 key。 |
| <a id="debugmetadataasset-uisourcemap"></a>`uiSourceMap` | [`UiSourceMapData`](#uisourcemapdata) | 入口运行时 UI 树的紧凑 UI source map。 |

### `FieldResolver` \{#fieldresolver\}

描述如何查找一个可查询字段，以及（可选地）
将匹配值的哪个子字段返回给调用方。

`resolve` 执行查找。`payload` 是可选的解包函数：对于
`source-map` 查询，resolver 返回完整的
[`SourceMapDebugSource`](#sourcemapdebugsource) 包装对象，而 HTTP 使用方通常需要
原始的 Source Map v3 JSON——`payload: sm => sm.map`
负责完成解包。

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| <a id="fieldresolver-payload"></a>`payload?` | `payload(value: T): unknown` |  |
| <a id="fieldresolver-resolve"></a>`resolve` | `resolve(metadata: DebugMetadataAsset, params: QueryParams): T \| undefined` |  |

### `SourceMap` \{#sourcemap\}

Source Map v3 数据，遵循 [Source Map Revision 3 提案](https://sourcemaps.info/spec.html)。

在此处声明（而非从 `source-map` 导入），是为了保持该包零依赖，
避免传递依赖方仅为了一个 TypeScript 类型

### `UiNode` \{#uinode\}

Lynx 引擎导出的 UI 树中的一个节点——即
[`remapUiTree`](#remapuitree) 的输入。会读取三个字段：`nodeIndex` 和
`debugMetadataUrl` 驱动反向解析，`children` 会被递归遍历。
这三个字段均为可选，因为引擎会产出不携带源码映射的节点
（例如 raw-text 节点没有 `nodeIndex`）；
这类节点会原样透传。其他字段均视为不透明数据。

| 成员 | 类型 | 说明 |
| --- | --- | --- |
| <a id="uinode-children"></a>`children?` | [`UiNode`](#uinode)`[]` | 子节点，会被递归遍历。 |
| <a id="uinode-debugmetadataurl"></a>`debugMetadataUrl?` | `string` | 覆盖该节点的 `debug-metadata.json` 的 URL/路径。 |
| <a id="uinode-nodeindex"></a>`nodeIndex?` | `number` | 编译期的节点标识，用于在 UI source map 中查找。 |

### `DebugMetadataLoader` \{#debugmetadataloader\}

```ts
type DebugMetadataLoader = (debugMetadataUrl: string) => Promise<DebugMetadataAsset>
```

加载节点 `debugMetadataUrl` 所指向的 [`DebugMetadataAsset`](#debugmetadataasset)。
由调用方提供，使核心逻辑不涉及 I/O（CLI 会接入
`fetch` / `fs`）；每个不同的 URL 只会调用一次。

### `DebugSource` \{#debugsource\}

```ts
type DebugSource = SourceMapDebugSource | BytecodeDebugInfoSource
```

附加到 [`Artifact`](#artifact) 上的一个调试数据源。

采用带标签的联合类型（tagged union），以便将来新增调试数据类型（例如 WASM debug info、
R-source-map）时无需调整 `artifacts[]` 的结构。
